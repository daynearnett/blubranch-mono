## Correction to a prior run's claim: there is no "nightly vouch-expiry job" that deletes anything

The 2026-11-02 log's side note said a code read found "a nightly `jobs/vouch-expiry.ts` that
deletes a pending vouch (and its notification) past that shelf life." **Re-read the actual code
today (`packages/api/src/routes/vouches.ts`) and no such file exists** — there is no
`jobs/vouch-expiry.ts` anywhere in `packages/api/src/jobs/`, and nothing in the codebase ever
calls `prisma.vouch.delete`/`deleteMany`. The only thing `PENDING_SHELF_LIFE_DAYS = 30` does is
add a `createdAt: { gte: shelfSince }` filter to the **`GET /vouches/pending` query itself** —
once a pending vouch crosses 30 days old, it simply stops appearing in that one list. The vouch
row stays in the database forever as `status: "pending"`, it never auto-resolves, `vouch-context`
between that pair (which has no date filter) will keep showing it as `received`/`given` forever,
and the original `vouch_received` notification is completely untouched either way (notifications
and the pending-vouch query are two independent surfaces with two independent, and differently
broken, lifecycles). **So when Vic's Oct-12 fabrication crosses 30 days around Nov 11, the
correct prediction is: it vanishes from `/vouches/pending`, but nothing else changes** — not the
"first real resolution path" the 11-02 log speculated it might be. Worth watching Nov 11 anyway,
just to confirm the query-filter behavior rather than an actual expiry/cleanup.
