## New finding: Crew Post coauthors don't surface the post in their OWN connections' feeds

Built today's w1+w2 crew post (Ray rewire + Tommy water-heater swap) end to end: `POST /posts`
with `coauthorIds:[w2]` → w2 saw the invite, `PUT /posts/:id/coauthor {"action":"accept"}` →
`status:"accepted"`. Likes/comments all round-tripped. But checking **w3's** feed (she's
mutually connected to w2/Tommy, not connected to w1/Ray) — the crew post never appeared, despite
her actual connection being a full accepted coauthor on it. Compared against w2's own feed, which
*does* show it (expected — Ray is w2's direct connection).

Root cause, read directly from `packages/api/src/routes/posts.ts` `GET /feed`: the connection
filter is `post.userId: { in: connectionIds }` — it only ever checks the post's **primary author**,
never the `coauthors` relation. So a crew post only reaches the primary author's network; a
coauthor's own connections — the whole point of tagging them as co-author — never see it in their
feed unless they're also connected to the primary author directly. **Severity: SHOULD-FIX.** This
quietly defeats half the value of the Crew Post feature (DIFFERENTIATION.md C1-adjacent — crew
posts are meant to be a two-sided flex).

## New finding: `GET /feed` omits `viewerCoauthorStatus` entirely (present on `GET /posts/:id`)

While confirming the above, noticed the feed's post shape for the same crew post has **no**
`viewerCoauthorStatus` key at all for w2 (pending invitee) — not `null`, just absent — while
`GET /posts/:id` for the identical post correctly returns `"viewerCoauthorStatus":"pending"`. If
the mobile accept/decline banner is driven off the feed payload (the natural place to show it,
since that's where you'd scroll past your own tagged post), a tagged user would never see the
banner there — only if they already got push/in-app notified and tapped through to the single-post
view. **Severity: SHOULD-FIX** — worth a mobile-side check of which payload actually drives that
UI banner.
