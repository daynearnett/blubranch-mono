## Headline: the malformed-id → raw Prisma 500 is not a `/jobs/:id`-only bug — same crash on `/companies/:id`

Tried `GET /companies/mine` for Hank (e1), expecting a "my company" convenience route. There
isn't one by that name — `mine` path-matched straight into `GET /companies/:id` with zero UUID
validation, same as the long-standing `/jobs/:id` finding: `500 {"code":"P2023", error:"Internal
Server Error", message:"Invalid prisma.company.findUnique() invocation... Error creating UUID...
found 'm' at 1"}` — unauthenticated-reachable (no auth header was even sent), verbatim Prisma
internals leaked. Confirmed via a read of `packages/api/src/routes/companies.ts` on `main`: `GET
/companies/:id` has the identical unguarded `prisma.company.findUnique({ where: { id } })` shape
as the jobs route. This means the bug class is systemic — any raw `:id`-param route without a
UUID-format check will leak the same verbatim error on a malformed id, not just jobs. Worth
widening the punch-list item from "guard `GET /jobs/:id`" to "guard every raw `:id` route."

## Net read for the day

No new launch-blockers surfaced today, and nothing on the existing watchlist got fixed — but the
notification-lifecycle bug hit new high-water marks on three separate accounts simultaneously
under completely ordinary jobs/employer/payments usage, with zero cold-vouch or network probing
involved, which argues the backlog genuinely never resolves on its own rather than being an
artifact of how the sim happens to poke the network surface. The day's one real new finding is
that the malformed-id → raw-Prisma-500 bug isn't scoped to `/jobs/:id` — the identical crash fires
on `/companies/:id`, found by accident while guessing a "my company" convenience route that
doesn't exist. That both strengthens the existing finding (confirmed systemic, not a one-off) and
is itself useful UX feedback: a nonexistent sub-route under an authenticated resource should 404,
not path-match into an unrelated `:id` handler and leak internals unauthenticated. Payments and
subscriptions remain the most solid surface in the app for the fourth week running — Basic
one-time payment, both subscription tiers, and the job-stats pipeline all behaved exactly as
designed. The location-blind `/jobs` finding is now understood at the root-cause level (PostGIS
disabled in the staging environment, not a bad query), which should help scope the fix as an infra
decision rather than a code hunt. The plumber-trade dead end and the `isFeatured`/`plan`-naming
no-ops are unchanged, still cleanly reproducible, still waiting on a fix.
