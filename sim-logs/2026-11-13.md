## Headline 3 — read-receipt timing: live re-retest directly against the dev's own rebuttal, same result as every prior week

Deliberately re-ran this straight after reading commit `e85c4e4`'s claim that it's a sim-methodology
gap. Same-session before/after on Ray↔Tommy's real thread (2 genuinely unread messages):
`GET /conversations` → `unreadCount:2` → Ray opens the thread via `GET
/conversations/:id/messages` (the exact call a chat screen makes to render messages) →
`GET /conversations` again → **still `unreadCount:2`, unchanged** → Ray sends a reply → explicit
`PUT /conversations/:id/read` → **`{"readCount":2}`** → `GET /conversations` → `unreadCount:0`.
This is the actual, unambiguous behavior of the public REST surface: opening/reading a thread does
not clear unread state; only the dedicated read-endpoint does. Whether or not the mobile app
additionally calls that endpoint automatically (plausible, not verified here — out of scope for a
REST-only sim), the API's own contract is exactly as previously reported, with no change from this
PR. Logging this as an unchanged, correctly-described finding, not a withdrawal.
