## Headline: `lat/lng/radius` on `GET /jobs` is silently ignored on staging — Cleveland worker sees only Columbus jobs, 140 miles out, with no distance shown and no error

Nina (w3, Cleveland OH, HVAC) searched `GET /jobs?trade=hvac&lat=41.4993&lng=-81.6944&radius=25`
— an explicit 25-mile radius around her own city. Got back 4 results, **all in Columbus, OH**
(~140 miles away), every one with `distanceMiles: null`. Same thing for w1 (Columbus) searching
with his own coordinates — `distanceMiles` is `null` on every result regardless of whether lat/lng
was supplied at all.

Read the code (`packages/api/src/routes/jobs.ts` `GET /jobs`): it's deliberate and documented
in a comment — `isPostGisEnabled()` is false on Railway's stock Postgres, so the whole geo
branch (`useGeo`) is skipped: no `ST_DWithin` radius filter, no distance column, `sort=nearest`
silently falls back to unsorted/default order. That's a reasonable fallback for an environment
without PostGIS, **but the API gives the client zero signal that this happened** — same 200,
same shape, `distanceMiles: null`, radius param silently accepted and silently not applied. A
real tradesperson in Cleveland who sets a 25-mile radius and gets jobs in Columbus has no way to
know the radius did anything other than get ignored. If staging is meant to approximate
production behavior, this is a real pre-launch question (is PostGIS enabled in prod? if yes, this
whole finding is staging-only infra noise; if PostGIS parity isn't guaranteed, the API should at
minimum flag `geoFilterApplied: false` or similar so clients can show "showing all jobs — can't
sort by distance right now" instead of implying a working radius filter). **Severity: SHOULD-FIX
(launch-blocker if prod also lacks PostGIS).**

## New finding: job trade category doesn't match job title ("Concrete Finisher" tagged as Welder)

Vic's (e3) own posting "Concrete Finisher — Commercial" is tagged `trade: {name: "Welder", slug:
"welder"}` on both `GET /jobs/:id` and the public search results. A concrete worker filtering
`GET /jobs?trade=concrete` will never see this job; a welder filtering `trade=welder` will see a
job that has nothing to do with welding. Likely a seed-data mislabel from an earlier run rather
than a live bug in the post-job wizard, but worth a spot-check of whether the real wizard makes
it easy to pick the wrong trade chip for a job title (no trade/title cross-validation visible in
the schema). **Severity: POLISH** (content hygiene, not a code defect we could isolate from here).

## New finding (minor, informational): `pay-insights` ignores the `trade` slug query param entirely

`GET /jobs/pay-insights?trade=plumber` and `?trade=heavy-equipment` (as w1, an electrician) both
silently returned Electrician numbers — the worker's own profile trade — with no validation error
and no acknowledgment that `trade` was received. The route only responds to a numeric `tradeId`
query param (confirmed: `?tradeId=11` correctly returned Heavy Equipment's `insufficient:true`).
If the mobile client (or anyone hand-building this URL) ever passes a trade slug instead of an id,
they'll get back *someone else's trade's numbers* with no error — easy to misread as "my trade's
pay data." **Severity: POLISH**, but worth a quick grep of the mobile call site to confirm it
always sends `tradeId`.
