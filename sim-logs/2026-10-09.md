## New finding: replying to a thread does NOT mark the other person's earlier message read

w1 (Ray)'s conversation with Deb Castillo (e2) showed `unreadCount: 1` today even though the
*last* message in the thread (back in August) was Ray's own reply to Deb. Pulled the raw messages:
Deb's original "Hi Ray... interested?" (Aug 19, 16:27:04) still had `readAt: null`, sent a reply
*after* it existed, and that reply obviously didn't touch the earlier message's read state —
because the only thing that marks a message read is a dedicated `PUT /conversations/:id/read`
call, and nothing calls it just because you typed a reply. `GET /conversations/:id/messages` also
does **not** mark anything read (fetched the thread, confirmed `readAt` was still `null`
afterward). So the unread badge for a conversation you've actually already engaged with and replied
in can sit lit up indefinitely unless the client explicitly fires the read-receipt call (e.g., on
thread-open, not only on reply-send). Whether this is a real bug depends entirely on whether the
mobile app calls `PUT /conversations/:id/read` at the right moment — worth a direct check against
the mobile client code. **Severity: SHOULD-FIX** (confirm mobile behavior; if it only marks-read on
reply, badges will drift out of sync with reality for every thread where the user reads-then-later
replies, or never replies at all despite reading).

## New finding: malformed job id crashes with a raw Prisma 500, leaking internals

Went looking for a "my jobs" listing for e1 (Hank) and guessed `GET /jobs/mine` before finding the
real route (`GET /users/me/jobs`, which works fine). The guess didn't 404 — it matched the
`GET /jobs/:id` dynamic route with `id="mine"` and crashed:

```
500 {"statusCode":500,"code":"P2023","error":"Internal Server Error",
"message":"Invalid prisma.job.findUnique() invocation: Inconsistent column data:
Error creating UUID, invalid character: expected an optional prefix of urn:uuid:
followed by [0-9a-fA-F-], found 'm' at 1"}
```

Repro'd again with a plain garbage string (`/jobs/not-a-real-id`) — identical 500 + full Prisma
error text verbatim in the response body. This isn't just an ugly error: it's leaking ORM/schema
internals to an unauthenticated client (no auth required on `GET /jobs/:id`), and any real-world
trigger of a non-UUID job id — a stale deep link, a cached id after a job's hard-deleted, a client
typo — would show a raw stack-flavored 500 instead of a clean 404. **Severity: SHOULD-FIX**
(wrap the `:id` param in a UUID-shape check before hitting Prisma, return 400/404 instead).

## New finding: notification feed noise could bury the exact signal this sweep cares about

w1's unread notification count was **17** today, almost entirely `daily_task` nudges (Oct 6, 7, 8,
all still unread, one per day, no natural resolution path since finishing the task doesn't mark the
nudge read) plus a backlog of `post_like`/`post_comment` from Tuesday's content day. The one
`job_match` and the handful of real social notifications are visually indistinguishable in the feed
from three-day-old task reminders. On a day explicitly about *messaging and notifications*, this
matters: the thing a user most wants to notice fast (someone messaged you) sits in the exact same
undifferentiated list, same unread styling, as "hop on and post a photo." (The one thing that *is*
well-separated: `/messages/unread-count` is its own independent endpoint from
`/notifications/unread-count`, so at least a message-specific badge is possible — good call in the
existing design, just not reflected in the combined `/notifications` feed itself.) Same root
pattern as Thursday's "a 51-day-old pending connection request just sat there" finding — stale,
un-resolving notifications accumulating with no escalation or cleanup. **Severity: SHOULD-FIX**
(either auto-expire `daily_task` notifications after ~48h, or give the feed a priority/grouping
pass so `new_message` and `connection_request` visually outrank task nudges).
