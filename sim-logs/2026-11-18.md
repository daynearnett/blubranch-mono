## Headline 1 — the PostGIS/Haversine radius-search bug (watchlist #6) IS genuinely fixed at the
math level — but a second, previously-invisible bug (no `GOOGLE_MAPS_API_KEY` on staging) makes
location search useless from any real worker's real coordinates right now

This is today's most important finding and needs to be read as two separate facts, because
conflating them would mis-diagnose the fix.

**Fact A — the distance math is fixed, confirmed live for the first time.** Posted a brand-new
Basic-plan job for Hank (Morrow Electric, Columbus OH) as part of today's required "fresh Basic
paid post," then drove it through the full headless Stripe test-mode flow end to end:
`POST /payments/jobs/:id/intent` → confirmed the returned PaymentIntent directly against Stripe's
REST API using the **publishable key as a Bearer token** + the client secret + `pm_card_visa`
(`POST https://api.stripe.com/v1/payment_intents/{id}/confirm`) → `status: succeeded` → BluBranch's
own `POST /payments/jobs/:id/confirm` backstop → `{"published":true,"status":"open"}`. Zero
friction, same mechanics as `stripe-e2e.ts`. Once that job had real, non-null coordinates, a
clean radius-differentiation test from a point ~480 miles away showed `radius=50` → `total:0`,
`radius=500` (the max) → `total:1` with `distanceMiles:306.8` reported correctly. **The PR #13
Haversine math genuinely works now** — this is the first live confirmation since the fix merged
Nov 11.

**Fact B — new finding: every job on staging geocodes to a point clustered near Chicago, not its
real city, because `GOOGLE_MAPS_API_KEY` isn't set.** The fresh job's real address was
"Columbus, OH 43215" — its stored `lat`/`lng` came back `41.8848006 / -87.6189584`, which is a
small deterministic offset from `services/geocode.ts`'s hardcoded `CHICAGO_FALLBACK` (`41.8781,
-87.6298`) used whenever `isGoogleConfigured()` is false. Searching from Nina's **real** Cleveland
coordinates (`41.4993, -81.6944`) at `radius=200` (the repro distance from the original Nov-11
finding) returns `total:0` — not because the filter is broken, but because the stored point is
~307 miles away near Chicago, genuinely outside 200 miles. Every pre-existing job in the DB
(the plumber listing, all of Hank's older electrician postings) still has `lat:null`/`lng:null`
(created before the fix landed Nov 11 ~18:04 UTC), so right now **zero jobs on staging have
real-world-accurate coordinates**, and any worker searching from their actual location at a
realistic radius (25–100mi) gets nothing, even for jobs objectively in their own city. Net effect
for a real user: location-based "jobs near me" looks exactly as broken as before the fix, for a
completely different reason. **Recommend:** set `GOOGLE_MAPS_API_KEY` on the staging Railway
service so new postings geocode correctly, and consider a one-off backfill job for the
pre-existing null-coordinate listings.

cheaper job ranked first with no visible "why") is a mobile-UI question this REST-only sim can't
adjudicate, not a missing server field.
