## Headline 1 — new finding: both employer subscriptions actually lapsed in Stripe on the same day, breaking a 35+ day clean-renewal streak

`GET /payments/subscription` for both Deb (Blu/`pro`) and Vic (Blu Max/`unlimited`) came back
`{"active":false,"status":"canceled","currentPeriodEnd":"2026-11-15T..."}` — the first time either
subscription has shown anything but a clean active renewal in 5+ weeks of monitoring, and it hit
**both** accounts on the **identical** `currentPeriodEnd` date. This was not a local-DB sync
artifact: `POST /payments/subscription/confirm` re-pulls straight from Stripe, and it independently
echoed `{"active":false,"status":"canceled"}` for both — meaning Stripe itself shows these
subscriptions as canceled, not just BluBranch's cached copy. Per the standing instruction, re-pulled
first (confirmed the cancel was real), then re-subscribed both headlessly the same way
`stripe-e2e.ts` does: `POST /payments/subscription/intent` → extracted the PaymentIntent id from the
returned `paymentIntentClientSecret` → confirmed it directly against Stripe's REST API using the
publishable key + `pm_card_visa` (`POST https://api.stripe.com/v1/payment_intents/{id}/confirm`) →
got `"status":"succeeded"` for both → `POST /payments/subscription/confirm` synced each back to
`active`. **Both plans are now live again**, `currentPeriodEnd: 2026-12-16`. Logging this as a
should-fix, not a launch-blocker (recoverable, and the recovery path worked cleanly) — but worth
investigating *why* two independent subscriptions, in different Stripe customers, lapsed on exactly
the same day after a 35-day clean streak. No code change in this sim window should have caused it;
possibilities worth a developer look: a missed/misrouted webhook event around the Nov-15 renewal
cycle, or something on the Stripe test-mode side. This is the first time payments — "the most solid
surface in the app, 5th+ week running" per the Nov-15 findings doc — has shown any crack.
